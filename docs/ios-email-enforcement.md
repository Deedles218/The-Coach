# COA-9222: обязательный email на iOS

Источник требований: [COA-9222](https://the-coach.atlassian.net/browse/COA-9222),
уточнение разработчика от 22 октября 2026 и **Manual steps / Expected Result**
в связанных Xray Test. Android в этот набор не входит.

`tests.IOSEmailEnforcementTests` использует существующие CoreTestCase,
Page Object, явные ожидания, onboarding, OTP и RestoringTestAction.
Каждый метод сохраняет ключ своего Xray-кейса в Allure.

| Xray Test | Метод | Независимые наборы |
|---|---|---|
| COA-9696 | `testCoa9696ProgressiveEnforcement` | E1 → E2 → E3, отдельно cross / later |
| COA-9697 | `testCoa9697FeatureOffUnlocksImmediately` | N / E3; применимый legacy-flow после OFF |
| COA-9698 | `testCoa9698UnavailableDailyDoesNotConsumeStage` | Показанный E1; следующий Daily действительно недоступен |
| COA-9699 | `testCoa9699KillAdvancesStage` | Отдельно E1 / E2 / E3 |
| COA-9700 | `testCoa9700UpdatePreservesStage` | Отдельно E1 / E2 / E3; более новая сборка того же bundle ID |
| COA-9701 | `testCoa9701RepeatedDailyDoesNotAdvanceStage` | Отдельно E1 / E2; другой доступный таб |
| COA-9702 | `testCoa9702SupportReturnsToMandatoryFlow` | N / E3, Support и последующая полная привязка |
| COA-9411 | `testCoa9411EmailConfirmationPreservesAccount` | N / E1 / E2 / E3; на обязательной форме также Change email и валидация |
| COA-9415 | `testCoa9415RepeatedSubmitCreatesOneFlow` | N / E3, доступное окно обработки для повторных нажатий |
| COA-9424 | `testCoa9424OccupiedEmailOffersLogin` | N / E3; известный занятый адрес, вход B не завершается |

Him и Her запускаются раздельно. Для старых пользователей состояния подписки
active/trial/expired/no purchase являются отдельными наборами при доступном Daily.
Само наличие методов не означает прохождение всей этой матрицы.

Согласованный объём: активный suite включает COA-9411, COA-9424,
COA-9696, COA-9699, COA-9701 и COA-9702. COA-9697 (OFF), COA-9698
(offline) и COA-9415 (повторная отправка) по решению владельца не требуют
автоматизации; в Jira им добавлен label `не_требует_автоматизации`.
COA-9700 (update) отложен. Их ранее созданные методы сохранены как черновики
и исключены из `IOSEmailEnforcementSuite` категориями `NotRequired` и
`Deferred`. Прямой запуск класса или отдельного метода обходит фильтр suite;
для рабочего набора используйте suite или явно выбранный активный метод.

## Фикстура и независимость

Стадия принадлежит **установке**, а не аккаунту. Перед каждым методом нужно
восстановить его исходное состояние. Смена аккаунта или повторный запуск
того же метода не восстанавливают E1. Набор не сбрасывает счётчики, не удаляет
аккаунты и не меняет Remote Config самостоятельно. После теста сохраняется
состояние для диагностики; OFF/offline восстанавливаются в `finally`.

Обычный запуск: один явно выбранный метод и один `.properties`-файл через
`-Dcoach.emailEnforcement.fixture=...`. Поле `case` должно совпадать с методом:
файл другого кейса отклоняется до открытия Appium-сессии.

`suites.IOSEmailEnforcementSuite` позволяет подключить набор к существующему
внешнему provisioning. Каталог `-Dcoach.emailEnforcement.fixtures=...` содержит
файлы `<имяМетода>.properties`. Между методами внешний runner обязан готовить
независимую установку/исходную форму; suite сам этого не делает. Для обычного
телефона используйте по одному методу после явной подготовки.

Обязательные поля файла:

```properties
case=COA-9702
bundleId=com.vamapps.preprod.The-Coach
app.version=1.13.34
app.build=3575
entry=prepared
stage=N
form.title=ENTER YOUR EMAIL TO SYNC YOUR PROGRESS
stage.N.message=So you never lose access if you switch phones or reinstall the app
daily.content=<наблюдаемый locator загруженного Daily, не таб Today>
```

Для N на Him 3575 есть наблюдаемый шаблон
`src/test/resources/email-enforcement/ios-preprod-him-3575-mandatory.properties`.
Для старого анонимного пользователя E1/E2/E3 используется
`src/test/resources/email-enforcement/ios-preprod-him-3575-existing.properties`.
Скопируйте его в `target/`, добавьте `case` и нужные поля.
Для других сборок/языков снимите собственные селекторы. E1/E2/E3 требуют
своих утверждённых `stage.E1.message`, `stage.E2.message`, `stage.E3.message`;
тексты предупреждений не выдумываются и не выводятся из проверяемого экрана.

`entry=prepared` требует `COACH_EMAIL_ENFORCEMENT_UID` текущего выделенного
анонимного аккаунта. `entry=new-user` начинает со штатного Welcome, проходит
опросник существующим helper и проверяет N; ожидаемый UID заранее не нужен.
Это режим подготовки **нового** профиля, а не способ превратить его в E1.
Оба режима требуют `ios.noReset=true`, `ios.fullReset=false`; reinstall-изоляция
отклоняется. При `new-user` Welcome и отдельная установка готовятся до запуска.

Дополнительные поля:

- COA-9696/9698/9701: `dismiss.action=cross` или `later`.
- COA-9701: `otherTab.control` (по умолчанию Explore) и `otherTab.content`,
  реальный маркер загруженного другого таба. Для Him 3575 проверены Shop
  и `Go beyond your program`.
- При закрытии E2: `stage.E2.warning.title`, `stage.E2.warning.message`,
  `stage.E2.warning.add`, `stage.E2.warning.later`. Основной текст формы
  совпадает с E1/E3; предупреждение о следующем обязательном запросе
  показывается отдельным экраном после cross / Remind me later. Тест
  проверяет текст, обе доступные кнопки и выбирает `MAYBE NEXT TIME`.
- COA-9698: `daily.unavailable`, наблюдаемый экран неудачной загрузки.
  Кэшированный доступный Daily приводит к ошибке предусловия.
- COA-9697: `legacy.outcome=daily` или `dismissible-form`, по ожидаемой
  старой логике; `legacy.abEnabled=true` / `false` фиксирует старый A/B-флаг.
  Его неизменность проверяется по активному конфигу. OFF снимается без relaunch.
- COA-9700: `update.app`, существующий `.ipa`/`.app`. Bundle ID, платформа
  и строго возрастающий номер сборки проверяются до установки.
- COA-9702: `form.support`, `support.destination`, `support.back`.
- COA-9411 на N/E3: `otp.changeEmail`, `email.placeholder`.
- COA-9415: `submission.pending`, наблюдаемый индикатор обработки. Ответ
  должен оставаться в обработке на время повторных taps. Быстрый ответ без
  этого окна не выдаётся за успешную проверку дублей.

OFF/offline требуют исполняемого `COACH_EMAIL_ENFORCEMENT_CONTROL` от владельца
тестового окружения. Он получает отдельными argv `action device bundleId`.
Действия: `feature-off`, `feature-restore`, `network-off`, `network-on`.
Команда возвращает 0 после фактического применения; настройка касается только
выбранного тестового окружения/устройства. Код не содержит Firebase write API.
Эти требования относятся к сохранённым черновикам, исключённым из рабочего
набора по решению владельца.

## Подготовка старого анонимного пользователя через TestFlight

На физическом тестовом iPhone доступен TestFlight (`com.apple.TestFlight`).
Инвентарь `devicectl device info apps` не перечисляет его, поэтому отсутствие
в этом выводе не является проверкой отсутствия приложения. Фактическое
открытие TestFlight через Appium подтвердило установку.

Для preprod for Him проверен следующий путь:

1. На выделенной тестовой установке удалить только
   `com.vamapps.preprod.The-Coach`. Это сбрасывает локальную историю показов;
   смена аккаунта или downgrade поверх текущей установки этого не гарантируют.
2. В TestFlight открыть `The CoachForHim: Preprod` → Previous Builds →
   `1.13.29, 6 Builds` → установить **1.13.29 (3417)**. Доступность старой
   сборки ограничена сроком TestFlight; перед повторением проверить её наличие.
3. Пройти штатный вход анонимного пользователя и закрыть paywall до Daily.
   Если Keychain восстановил выделенный тестовый анонимный аккаунт, повторный
   опросник не нужен. Проверить отсутствие email/подтверждения и сохранить
   digest UID, подписку и контрольные счётчики прогресса через reader.
4. В TestFlight обновить эту установку до **1.13.34 (3575)** без удаления
   между версиями. Проверить фактический build, совпадение UID и счётчиков,
   отсутствие привязанного email и активный конфиг.
5. При `launchesBeforeShow=3` первые три холодных открытия загруженного Daily
   проходят без запроса. На четвёртом показан E1. Остановить подготовку на
   открытой форме, не закрывать её и не перезапускать приложение до теста.

Appium-сессии подготовки и теста идут последовательно, с `noReset=true`,
`fullReset=false` и без принудительного перезапуска при создании сессии.
Методы COA-9701/9699 с E1 дополнительно закрывают ожидаемую E2, проверяют её
предупреждение и выбирают `MAYBE NEXT TIME`: одинаковая основная форма E1/E2
сама по себе не доказывает продвижение стадии. Эти прогоны заканчиваются
на Daily после закрытия E2. Наборы с исходной E2 заканчиваются на E3.
Продолжать с открытой формы можно только после проверки фактического состояния
и назначения соответствующей фикстуры.
Для нового независимого E1 повторить подготовку с чистой старой установки.

Обновление 3417 → 3575 здесь подготавливает существующего пользователя.
Оно **не считается выполнением COA-9700**, который проверяет перенос уже
накопленной истории E1/E2/E3 и пока исключён из автоматизации.

## Данные и доказательства

Секреты передаются через существующие переменные проекта:

- `COACH_VALID_EMAIL_WITHOUT_PROGRESS`: свободный адрес выделенного тестового
  почтового ящика для полной привязки;
- `COACH_EXISTING_PROGRESS_EMAIL`: известный адрес другого тестового аккаунта
  для COA-9424;
- `COACH_EXISTING_PROGRESS_OTP`: действующий тестовый OTP preprod.

Нельзя использовать произвольный адрес в COA-9424 или привязывать адрес общего
пользовательского аккаунта к одноразовому профилю. После успешной привязки
адрес уже занят: следующему независимому прогону нужен новый выделенный alias.
Покупки и сброс прогресса для этих проверок не требуются.

`scripts/read_ios_email_enforcement.py` работает с iPhone и Simulator. Он
читает фактически установленную версию, активный конфиг соответствующего
приложения и URL cache вместе с WAL-файлами. SDK UID и свежий JWT должны
совпасть с выделенной фикстурой до обращения к API. Используются только GET
`/api/v1/user/` и `/api/v1/user/achievments/` с запретом redirects.

В Allure попадают digest UID, boolean подписки/подтверждения email и три
контрольных счётчика прогресса. Адреса и токены reader не выводит. До OTP
проверяется отсутствие завершённой привязки; после OTP — нужный email,
подтверждение, сохранение исходного аккаунта/прогресса, Profile и новый
холодный запуск без запроса. Это контрольные счётчики из кейса, не проверка
каждого урока, выбранной программы или всего серверного аккаунта.

Пример одного прогона после подготовки формы и секретов:

```bash
mvn -q test \
  -Dtest=tests.IOSEmailEnforcementTests#testCoa9702SupportReturnsToMandatoryFlow \
  -Dplatform=ios -Dios.udid="$IOS_UDID" \
  -Dios.deviceName="$IOS_DEVICE_NAME" -Dios.platformVersion="$IOS_PLATFORM_VERSION" \
  -Dios.bundleId=com.vamapps.preprod.The-Coach \
  -Dios.noReset=true -Dios.fullReset=false -Dios.useNewWDA=false \
  -Dcoach.emailEnforcement.fixture=target/email-enforcement/coa9702.properties
```

Локальные проверки без UI:

```bash
python3 -m unittest discover -s scripts -p test_ios_email_enforcement.py -v
mvn -q test -Dtest=tests.EmailEnforcementScopeUnitTests,tests.EmailEnforcementFixtureUnitTests,tests.EmailEnforcementArtifactUnitTests,tests.LoginFailureScreenshotUnitTests
```

## Проверка 6 ноября 2026

Физический iPhone Daria (2), iOS 18.0.1; preprod for Him 1.13.34 (3575),
English, активный `force_connect_email_config.isEnabled=true`,
`launchesBeforeShow=3`. Проверенные наборы: новый анонимный пользователь N
и старый анонимный пользователь после TestFlight 3417 → 3575;
подписки нет, контрольные счётчики прогресса 0. Для успешных привязок
использовались разные выделенные alias тестового почтового ящика.

| Кейс | Итоговый результат | Фактическая проверка |
|---|---|---|
| COA-9424 | PASS | Известный занятый email → предложение Login; UID, подписка и прогресс исходного аккаунта сохранены, привязки нет |
| COA-9411 | PASS | OTP; Change email возвращает пустую обязательную форму; пустой/неверный адрес не пропускают; подтверждение, Profile, сохранение аккаунта и холодный запуск без запроса |
| COA-9702 | PASS | Support → FAQ → Back → обязательная форма → OTP → успешная привязка; сохранение аккаунта/подписки/прогресса и холодный запуск |
| COA-9696 | PASS, отдельно cross / later | E1 → E2 с предупреждением → обязательная E3; после следующего холодного запуска E3 сохраняется, контент недоступен |
| COA-9699 | PASS, отдельно E1 / E2 / E3 | Kill без закрытия: E1 → E2 с предупреждением, E2 → E3, E3 → E3; аккаунт не изменён |
| COA-9701 | PASS, отдельно E1 / E2 | Три перехода Shop → Today без повторного запроса; холодный запуск → следующая стадия, E2 подтверждена предупреждением |

Команды UI: `mvn -q test -Dtest=tests.IOSEmailEnforcementTests#<метод>`
с параметрами выше и отдельной подготовленной фикстурой. Локальные команды
из предыдущего блока: **12 Java + 5 Python проверок прошли**. Компиляция
выполнена через `mvn -q -DskipTests test-compile` и целевые Maven-прогоны.

Отчёт `target/email-enforcement/allure-report/` собирается по последнему
результату каждого активного метода, независимо от статуса результата.
Диагностические попытки остаются в исходном `target/allure-results/`
и логах `target/email-enforcement/`.
Итоговый последний срез: **6 passed / 0 failed / 0 broken**. Три ранее
проверенных кейса на N и семь наборов E1/E2/E3 дают **10 успешных наборов
по 6 активным кейсам**. Для COA-9696 сохранены отдельные логи
`coa9696-E1.log` и `coa9696-E1-later.log`; для COA-9699 — `coa9699-E1.log`,
`coa9699-E2.log`, `coa9699-E3.log`; для COA-9701 — `coa9701-E1.log`,
`coa9701-E2.log`. Все находятся в `target/email-enforcement/`.

Первый COA-9702 после COA-9424 и Cancel на предложении Login дошёл до отправки
свободного адреса и получил `Email not found. Contact support below.`.
XML: `target/page-source/testCoa9702SupportReturnsToMandatoryFlow.xml`,
лог: `target/email-enforcement/coa9702.log`. Вероятный источник — повторное
использование контекста предыдущего flow; связь с Cancel требует отдельного
воспроизведения. На независимом новом профиле COA-9702 прошёл. Это не
подтверждённый дефект самого перехода в Support. Проверка Cancel → свободный
адрес остаётся отдельным следующим исследованием.

Ранние попытки COA-9701 исправлены на уровне теста/фикстуры: устаревший маркер
Shop заменён на наблюдаемый `Go beyond your program`, после закрытия E2
добавлена обработка отдельного предупреждения. Предположение об отсутствии
предупреждения E2 опровергнуто его фактическим показом и успешным прогоном.

Во время подготовки COA-9696 выявлено расхождение screenshot/XML: paywall
виден на телефоне, но WDA возвращал пустое дерево элементов. Перезапуск WDA
восстановил дерево. В подготовку добавлено явное ожидание формы/загруженного
Daily. Одна попытка теста завершилась в setUp с `Daily email form is absent`
после прерванной подготовки; после восстановления правильной E1 тест прошёл.
Это проблемы подготовки и драйвера, а не подтверждённые дефекты COA-9222.

На наборе `dismiss.action=later` первая попытка прошла закрытие E1, но после
холодного запуска остановилась при ожидании E2: в XML оставался paywall.
Причина — обработчик paywall вызывался ещё на экране запуска и завершался
до появления paywall. В Page Object добавлено ожидание видимого известного
экрана перед обработкой промежуточных экранов; проверки E1/E2/E3 сохранены.
Повторная подготовка останавливалась на отсутствии интернета в TestFlight.
После восстановления подключения подготовлена новая E1; повторный UI-прогон
`later` с исправленным ожиданием **прошёл полностью** (70.604 секунды).

**Не автоматизируются по решению владельца:** COA-9697, COA-9698, COA-9415.
**Отложен:** COA-9700. Подготовка через TestFlight не подменяет его проверку.
Вариант Her, Simulator и остальные состояния подписки этим прогоном не проверены.

В `CoreTestCase` добавлено распознавание нового OTP по тексту отправленного
кода: цифры маскируются в XML, screenshot с OTP не сохраняется. Существующие
проверки защиты старого OTP и login screenshot также прошли.
