# COA-8511 / COA-8512 — Kegel Challenge

Пользователь разрешил подготовку Kegel Challenge на том же Premium-аккаунте:
смену варианта, дня и при необходимости сброс прогресса программы. Удалять
аккаунт, менять другие программы, подписку или глобальные флаги нельзя.
Разрешение хранится отдельно как `kegelMutationScope` в локальном Keychain
`the-coach-test-model-premium`. Старые disposable-аккаунты не перезаписываются.

## Реализация

1. Проверяем соответствие UID/почты, текущую simulator identity и Premium.
2. Выбираем Kegel Challenge, открываем её Settings и выполняем UI Restart Program
   с точным подтверждением сброса **программы**, не аккаунта.
3. API готовит первый перенос `exercise_kegel_sport_w1_t1` / Resistance Kegel
   Training с дня 1 на 2 и завершает остальные задачи дня 1. Проверяются
   `is_moved_forward`, тот же action ID, секция TO CATCH-UP и невыполненное состояние.
4. Для COA-8512 завершаем остальные задачи дня 2; проверяем ровно одну оставшуюся
   невыполненную задачу среди **всех** задач, не только изменяемых.
5. Второй перенос на дне 2 выполняет **UI long-press → Move to tomorrow**.
   API подготовки принципиально не позволяет выполнить второй перенос.
6. COA-8511 проверяет часы и ту же карточку в TO CATCH-UP дня 3 (Stage 3 of 9).
   Плановая карточка с таким же названием не может заменить перенесённую:
   UI-локатор учитывает ближайший заголовок секции, API — action ID + section ID.
7. COA-8512 сравнивает фактический процент до переноса, после него и после
   закрытия/открытия приложения. Ровно 2% не требуется по уточнению пользователя.
8. В `finally` возвращаем Last Longer: Retain и проверяем прежние Day 42 / 27%.
   Первичная ошибка сохраняется вместе с ошибкой восстановления, если та есть.
   UI/XML/скриншот ошибки снимаются до восстановления.

Kegel Challenge остаётся тестовой программой с изменённым прогрессом: её
исходные 12% не восстанавливаются после разрешённого сброса. Сбросы повторены
при перезапусках, свежие предусловия подтверждаются перед каждым сценарием.

Файлы: `TestModelAutomationTests`, `iOSKegelCustomizationPageObject`,
`iOSExplorePageObject`, `TestModelFixtureSupport`, `test_model_kegel_fixture.py`,
bridge/runner и offline-проверки. Общий disposable guard и отдельное старое
разрешение Overall Health сохранены.

## Запуск и результаты

```bash
python3 scripts/run_test_model_local.py COA-8511 COA-8512 --maven=-q
```

Запуски строго последовательные. При ошибке первый процесс останавливает
последовательность; не происходит скрытого перехода на старый алиас или retry.
Для исправленного второго сценария используется отдельный запуск COA-8512.

- COA-8511 — **PASS**, 167.320 с по Surefire, 166.735 с по Allure.
  `target/allure-results/abd6809b-3acb-40bf-a453-e1c0701e5aa4-result.json`.
- COA-8512 — **PASS**, 182.706 с по Surefire, 182.132 с по Allure.
  `target/allure-results/549349d9-664e-4436-848f-e03cfb5f097f-result.json`.
  Фактический прогресс: **2% → 2% после переноса → 2% после перезапуска**.
  Значение измерено в UI и не захардкожено в ожидании.

Оба сценария завершились с успешной проверкой возврата Last Longer: Retain,
Day 42, 27%. Аккаунт не удалялся. `kegelTestExit` содержит 0 для обоих кейсов,
а `kegelFixtureReady=true` отражает проверенный повторяемый reset/setup.
Доказательства прогресса COA-8512: Allure attachments
`55e9d4e0-6234-4949-9a60-388355492e18-attachment.txt` (после переноса) и
`91304f16-21a7-4c1c-a2ae-9ca1f7f0e5a4-attachment.txt` (после перезапуска).

До финальных результатов исправлены ошибки тестовой инфраструктуры:

- Текст подтверждения reset находится в `label` элемента `TitleBlock.Title`,
  не в `name`. Первый запуск остановился **до** подтверждения сброса.
- После перезапуска могут появляться notification / workbook upsell overlays.
  Они закрываются штатными методами, покупки не выполняются.
- На дне 3 допустимы одноимённые плановая и перенесённая практики. Проверка
  уникальности теперь ограничена TO CATCH-UP, а не только названием карточки.
- После завершения остальных задач приложение может уже открыть Stage 2 при
  перезапуске. Setup проверяет фактический этап и не делает лишний переход на 3;
  перед бизнес-действием обязателен точный Stage 2 of 9.
