### Изоляция новых сценариев и подготовка

Используются существующие `CoreTestCase`, Page Objects, explicit waits и
`MobileCaseFixture`. Проверенные открытые ожидания сохранены в
[`ios-preprod-3609.properties`](../src/test/resources/program-activation/ios-preprod-3609.properties).
Для отдельной первой активации без Main используется
[`ios-preprod-3609-no-main.properties`](../src/test/resources/program-activation/ios-preprod-3609-no-main.properties).
Новая анкета Beat premature ejaculation и альтернативная Main Keep It Hard
описаны в [`ios-preprod-3609-last-longer.properties`](../src/test/resources/program-activation/ios-preprod-3609-last-longer.properties).
Это разные исходные состояния, а не один общий профиль для последовательного suite.
Указывайте `COACH_PROGRAM_SELECTION_CASE` и UID своего
QA-профиля. Для подтверждённого профиля нужен `COACH_PROGRAM_SELECTION_EMAIL`.
На первом входе отдельный свободный QA-адрес и OTP передаются через
`COACH_PROGRAM_SELECTION_NEW_EMAIL` / `COACH_PROGRAM_SELECTION_NEW_OTP`.
Привязка адреса проверяет тот же исходный UID и сохранность ролей/прогресса;
не допускается замена email зарегистрированного профиля. Секреты не передаются
в Maven arguments или fixture properties.

Для пункта с обязательным вопросом используйте пары
`COA-9802.first.item.question` / `COA-9802.first.item.answer` либо
`COA-9794.switch.item.question` / `COA-9794.switch.item.answer`.
Они проверяются до переключения/Start;
helper выбирает только заданный ответ при появлении заданного вопроса.
Новый метод завершения пункта закрывает штатное предложение уведомлений через
существующий `CoachFlowPageObjectFactory`. Проверка повторов tutorial использует
переключение без автоматического закрытия подсказок.

Обычный вход COA-9790 после успешного Paywall по-прежнему проверяет Premium.
Отдельный `-Dcoach.programSelection.entry=secondary` предназначен только для
нового preprod-профиля уже на Secondary с Main и пустым сохранённым набором:
`-Dcoach.programSelection.mainId=<reviewed_id>`. Этот вариант проверяет
именно контракт COA-9790 и не выдаёт обход Paywall за успешную покупку.

В `ProgramPaywallEntryTests` нужны существующие явные флаги
`-Dstorekit.sandbox=true -Dpurchase.allow=true`, исходный Paywall и собственный
новый UID на каждый исход. Подтверждение разрешено только при явном нативном
уведомлении о тестовой покупке без списания. Пароль берётся из секретного
runner, без аннотированных шагов и сохранения в репозитории. Для приобретения
на устройстве Appium request logging должен быть отключён. Два подтверждённых
тестовых тарифа дали серверный `subscription.active=true`: Special Offer
`1M.9.99.NoFT.preprod` на первом чистом QA-профиле и обычный
`1M.19.99.NoFT.preprod` на втором. Эти исторические результаты подготовки
учитываются отдельно. Позднее оба входа прошли как полные JUnit-проверки
`ProgramPaywallEntryTests` на новых QA3 и QA4.

API-reader использует безопасный список GET и проверяет SDK/API identity.
Legacy `catalog/v3/<program>/` не используется как read-only oracle: во время
диагностики он изменил Active на выделенном QA-профиле. Исходная Main затем
возвращена обычным UI; последующий A→B→A прошёл со строгим сравнением снимка.
Реальные пользовательские профили для такой подготовки не используются.
Кэшированные внутренние заголовки `__hhaa__` не отправляются повторно.

Проверка ответов Main, Secondary, Complete и Add читает запрос и ответ текущего
UI-действия из кэша и проверяет UID, HTTP-статус, маршрут и время. Для Complete
и `POST /api/v1/coachprogram/<program_id>/add_and_activate/` допускается
наблюдаемый iOS-маркер пустого тела `__CFURLRequestNullTokenString__`.
У Add ID находится только в URL, тело отсутствует; это подтверждено нативным
кэшем и контрактом COA-9729. Остальные POST требуют точный JSON.
Точечные проверки: 50 Python tests API/HTTP-cache — PASS; ещё 20 тестов
чтения текущего контента — PASS; 8 тестов прокрутки и безопасного открытия
селектора — PASS. Полный regression
не запускался.

Пример точечного запуска (профиль и секреты уже переданы runner через env):

```bash
mvn -q -Dplatform=ios -Dios.bundleId=com.vamapps.preprod.The-Coach \
  -Dios.udid="$IOS_UDID" -Dios.deviceName="$IOS_DEVICE_NAME" \
  -Dios.platformVersion="$IOS_PLATFORM_VERSION" \
  -Dios.noReset=true -Dios.fullReset=false -Dios.useNewWDA=false \
  -Dtest.isolation.mode=logout -Dappium.url=http://127.0.0.1:4817/ \
  -Dcoach.mobileCases.fixture=/path/to/reviewed.properties \
  -Dtest=tests.ProgramOnboardingScenarios#startOpensMainDailyPlanAndPersistsExactlyTheSummaryPrograms test
```

Эксперимент [COA-9710](https://the-coach.atlassian.net/browse/COA-9710) управляет
онбордингом, селектором и Explore одновременно. В Firebase используются
`abtest_program_onboarding_v1` для Him и `abtest_program_onboarding_v1_for_her`
для Her. Подбирайте профиль с подтверждённой группой для каждого варианта
приложения. Номер сборки сам по себе группу не определяет.

## Ограничения общей базы и Firebase

У prod и preprod общая база аккаунтов. Запуск через preprod не изолирует
изменения выбора программ, прогресса и завершённости онбординга от продового
аккаунта. Для записывающих сценариев нужен конкретный выделенный QA-профиль
с подходящим исходным состоянием; автоматически перестраивать готовый профиль
ради прохождения предусловий нельзя.

По прямому правилу владельца Firebase-конфиги **prod и preprod меняются только
после его явного разрешения**. Это правило относится и к подготовке тестов.
В этой работе Firebase-конфиги не менялись. Авторизация в Elixir/Django preprod
использовалась для просмотра QA-инструментов; формы изменения данных там
не сохранялись.

| Группа | Набор | Подготовка |
| --- | --- | --- |
| OFF | Действующие `suites.OnboardingGoalProgramSuite`, `suites.TestModelAutomationSuite` и наборы Explore | Профиль со старым онбордингом, прежним селектором и каталогом. Используйте предусловия каждого набора. |
| ON | `suites.ProgramActivationSuite` | Профиль с завершённым новым онбордингом. На Today видны активная программа, стадия и первый урок. Подсказки закрыты, активная строка видна при открытии My Programs. Для проверки прокрутки Add a program изначально находится вне видимой части списка. |

В `ProgramActivationSuite` есть три проверки [COA-9805](https://the-coach.atlassian.net/browse/COA-9805).
Первая проверяет отметку активной программы и закрытие селектора жестом и тапом
снаружи. Вторая открывает All Programs через Add a program. Обе сверяют программу,
стадию и первый урок после возврата в Today. Третья прокручивает длинный список
вниз до Add a program и обратно к исходным строкам, сверяет активную программу,
затем повторно прокручивает список и открывает каталог. Проверка отличает
смещение строк от движения самой шторки. Нужен профиль и размер экрана,
при которых Add a program изначально находится за нижней границей списка.
Короткий список завершает тест ошибкой предусловия, а не успешным результатом.
Метка `автоматизировано` отражает наличие кода; результат UI-прогона фиксируется
отдельно и не выводится из наличия метки.

## Запуск ветки ON

Запускайте отдельно для Him и Her через существующий Appium/XCUITest. Укажите
`IOS_UDID`, `IOS_DEVICE_NAME` и `IOS_PLATFORM_VERSION` по [локальной инструкции](local-setup.md#52-настоящий-iphone).
Текущая среда прогона — установленные preprod-сборки с подготовленными
тестовыми профилями: `IOS_BUNDLE_ID=com.vamapps.preprod.The-Coach` для Him
либо `com.vamapps.preprod.The-Coach-for-her` для Her. Dev-сборки имеют
суффикс `develop` вместо `preprod`, но их нестабильность фиксируется отдельно
и не подменяет результат preprod. Путь `IOS_APP` и отдельный
`IOS_SESSION_BUNDLE_ID` для этого прогона оставьте пустыми.

```bash
mvn -Dtest=suites.ProgramActivationSuite -Dplatform=ios \
  -Dios.noReset=true -Dios.fullReset=false -Dtest.isolation.mode=logout test
```

`logout` здесь выбирает режим без переустановки в `CoreTestCase`. Набор закрывает
свои экраны и завершает сессию Appium, сохраняя вход в тестовый профиль. При
попадании в старый селектор ожидание My Programs завершается ошибкой с подсказкой
проверить группу A/B. Подготовка использует существующий
`closePaywallsAndPopups()` для стартовых paywall и необязательных предложений.
Обязательный ввод email этот helper не обходит: заранее войдите в подтверждённый
QA-профиль. Продовые QA-аккаунты подходят для входа в preprod, однако роли программ
и прогресс для конкретного Xray-кейса нужно проверить в этой среде отдельно.
Отчёты сохраняются в `target/allure-results`.

конфига. Обычные UI-проверки запускаются на действующем preprod-конфиге.

## Ранние результаты 21 ноября: COA-9790 и COA-9799

`ProgramSecondarySelectionTests` покрывает три основных шага COA-9790:
пустой выбор, счётчик 1 → 2 → 1 и две программы в Summary без дублей. Перед
действиями `ProgramSelectionApi.assertFreshOnboardingProfile()` только читает
данные и требует новый профиль без Main/Secondary, завершённого выбора и
прогресса, с действующим доступом после успешного Paywall. Затем приложение
должно уже находиться на Recommendation. Каждый метод требует независимого
профиля и оставляет Summary для проверки. Очистка не нажимает Start и не выходит
из аккаунта. Сами шаги теста сохраняют черновик выбора; это не проверка без
изменения данных. Условная граница 3/4 из описания Xray остаётся зависимой
от согласованного правила лимита.

По решению владельца COA-9799 отложен с меткой
`automation-deferred-api-validation`. Класс `ProgramSelectionApiTests` помечен
`@Ignore`: его обычный запуск подтверждён как 1 skipped, 0 failures/errors.
Реальные недопустимые запросы в этом запуске не отправлялись. Код сохранён
для будущего разбора, дальнейшая реализация и запуск этих проверок прекращены.
Ранее добавленные методы проверяют Main в Secondary (400), активацию
недобавленной программы (400) и завершение без Main (409). Сверяются доступные
поля ролей, активная программа, каталог, прогресс и флаги завершения. При
неожиданной записи клиент пробует восстановить исходное состояние через
обычные API; отсутствие успешного восстановления завершает тест ошибкой.
Нулевой риск изменения данных при дефекте API этим не гарантируется.

Зарегистрированный QA-профиль привязывается через переменную окружения
`COACH_PROGRAM_SELECTION_EMAIL`; анонимный — через `COACH_PROGRAM_SELECTION_UID`.
Они должны соответствовать текущему входу в установленном приложении.
В командную строку и Allure email, UID и токены не передаются. Заголовок
`X-Gender` соответствует фактически наблюдаемым запросам приложения: `M`/`F`.
